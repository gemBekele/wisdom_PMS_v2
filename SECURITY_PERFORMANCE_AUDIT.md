# Wisdom SACCOS PMS — Security, Performance & Business Logic Audit

> **Update (2026-10-29):** A subsequent deep-test/hardening pass fixed the public user directory, JWT revocation, key IDOR paths, CBS idempotency, June import transactions, score scheduling, score caps, non-deposit KPI counts, upload handling, unique constraints, and vulnerable `xlsx`/`react-router` versions. See `DEEP_TEST_REPORT.md` for the final state and remaining gaps.

Date: 2026-10-29
Scope: `backend/` and `frontend/` of the Wisdom-SACCOS-PMS repository.

This audit is based on full route/controller/schema review, page-by-page frontend review,
`npm audit`, production builds, and runtime checks against the local PostgreSQL database.

---

## 1. Executive summary

The system is functional and the Wisdom rebrand is complete, but it still contains
several high-risk authorization gaps and major N+1/aggregation performance problems.

**Highest-risk items still open**

1. Public user directory + password login without MFA enables enumeration and targeted credential attacks.
2. Several financial read/write endpoints still rely only on `protect` or role-only checks (CBS upload branch choice, exports, mapping bulk import, some plan/staff-plan reads).
3. Financial imports/mutations (CBS, June baseline, bulk mapping) are not transactional; failures can leave partial balances, tasks, and schedules.
4. Performance scores are not generated by any normal workflow; KPI/behavioral period models are incompatible.
5. Dependency vulnerabilities: `xlsx`, `react-router`, `vite`/`vitest`, `ws`, `lodash`, etc. (see §2).

**Fixed in this repository**

- Privilege escalation via `PUT /api/users/:id` (admin-only + field allowlist).
- Password hashes/reset tokens leaked by user/profile APIs.
- Staff/manager query-parameter scope widening on `/api/users` and `/api/tasks`.
- Self-approval/self-evaluation and cross-branch behavioral approvals.
- NPL installment payments: manager-only, branch-scoped, amount/date validated.
- CBS discrepancy resolution: manager-only, validation/branch-scoped, notes required, audited.
- Mapping updates: whitelist fields, branch scope, assignee branch validation.
- Global balance-source setting is now admin-only.
- Login/API rate limiting, Helmet security headers, gzip compression, strict 500 responses.
- N+1 baseline lookups in `calculateIncrementalGrowth` (now 2 queries per user).
- 20+ hot-path database indexes and audit enum additions.
- Route-level code splitting: initial JS dropped from ~1.17 MB / 315 KB gzip to ~425 KB / 129 KB gzip.
- ResponsiveTable no longer renders every row twice.
- Notification open-redirect/XSS sink replaced with same-origin router navigation.
- API client now handles 204/empty bodies, timeouts, and 401 logout.
- Plan upload validator repaired (accepts KPI names and legacy product names, maps product enum).
- Plan create/update field whitelisting + product category normalization.
- KPI score weights hoisted and normalized; rating thresholds made reachable and consistent.
- June baseline import no longer deactivates the active baseline before a successful parse.
- Migration drift fixed (`users.teamId`, duplicate TaskType enum values) so fresh installs work.

## 2. Dependency vulnerabilities (`npm audit`)

Run `npm audit` in `backend/` and `frontend/` for the current counts. Most important:

| Package | Severity | Area | Recommended action |
|---|---|---|---|
| `xlsx@0.18.5` | High | User-uploaded Excel/CSV parsing | Upgrade to current SheetJS vendor release (≥0.20.2); add row/size/time limits. |
| `react-router` / `react-router-dom` | High | XSS/open redirects, DoS advisories | Upgrade to latest patched 7.x; re-test routes. |
| `vite` / `vitest` / `tinypool` | Critical/High (dev) | Dev server / test runner | Upgrade; these are dev-only but must not be exposed. |
| `ws` | High | Memory disclosure/DoS | Upgrade transitive dependency. |
| `lodash`, `minimatch`, `picomatch`, `js-yaml`, `form-data` | High | Transitive | Run `npm audit fix` and re-test; pin patched versions. |
| `proxy-addr` | Critical | IP spoofing via trust proxy | Upgrade; keep `trust proxy` set only to the real reverse proxy. |
| `body-parser` / `qs` | High | DoS via malformed payloads | Upgrade via `express` update. |

`npm audit fix` is safe for some transitive packages, but `xlsx`, `react-router`, and
Vite/Vitest need deliberate major/minor upgrades and regression testing.

### 3.2 Fixed in this repository

- `PUT /api/users/:id` now requires admin and uses an allowlist; password hashing, role
  validation, supervisor/branch consistency, and self-supervision checks added.
- `getUsers`, `getUser`, `getMe`, and `updateDetails` no longer return `password`,
  `resetPasswordToken`, or `resetPasswordExpire`.
- Non-admin query parameters can no longer widen `/api/users` or `/api/tasks` scope.
- `getTask` now enforces owner/branch access.
- Behavioral evaluations: no self-evaluation, same-branch enforcement, real approver
  roles only, no self-approval, status whitelist.
- NPL installment payment: manager-only, branch-scoped, positive amount, valid date.
- CBS discrepancy resolution: manager-only, validation ID + branch check, required notes,
  audit entry.
- Mapping updates: safe field allowlist, branch scope, assignee branch validation.
- Global `balance-source` setting is admin-only.
- Login and API rate limits; Helmet headers; 2 MB body limit; generic production 500s.
- JWT secret validation; `.env` ignored; `SETUP.md` no longer publishes a real secret.

## 5. Business logic gaps by domain

### Users, roles, hierarchy

- **Critical:** Users created from `UserManagement` previously got `branch_code` but no
  `branchId`, and `supervisorId` was ignored. Creation now resolves branch/area and
  stores supervisor, but the UI still needs to send/validate these consistently.
- No enforced role↔position matrix; any role/position combination is accepted.
- Supervisor cycles/self-assignment are now blocked for self, but deeper cycles are not.
- Deactivating managers does not clear `supervisorId`, `teamId`, `Area.managerId`, or
  `Branch.managerId`.
- Branch/area renames do not cascade denormalized `branch_code`/`areaId` values.
- Area/region/branch CRUD has no audit logging; region display is broken (`Branch` no
  longer has `regionId`); no region/area management UI.

### Plans and plan cascade

- **Critical (fixed):** Bulk plan upload rejected every valid KPI and accepted product
  names that were not `KpiCategory` values. Now maps KPI/product display names to enum
  values and creates plans successfully.
- Plan + staff-plan creation/replacement is still not transactional; cascade failures
  can leave orphan or missing staff plans.
- `target_count` and imported `monthly_plan` are stored but not used in scoring; score
  calculations are growth-only.
- Percentage KPIs (`Collection Rate`, `Portfolio Quality`) still use deposit product
  share allocation (35/25/15/25), producing meaningless targets.
- No uniqueness constraint for `(branch, kpi, product, period)` or
  `(branchPlanId, userId)`; duplicate active staff plans are possible.
- No staff-plan edit/reassignment UI/API; no plan delete/cancel/status transitions.
- Plan achievement only maps task types for `Deposit_Mobilization`; other KPIs always
  show 0 actual.
- Baselines are not tied to the plan period; performance always uses `is_active = true`
  rows regardless of period.

### Tasks, approvals, edit requests

- New-account task creation immediately creates an Active owner mapping, bypassing the
  advertised branch-manager mapping approval.
- Approval chains can be empty or contain the same approver twice; tasks can stall
  forever. No fallback to area/admin and no reassignment.
- Edit requests can be approved after the task is already approved; they do not reset
  the approval chain, update `accountId`/`mappingStatus`/`cbsValidated`, or recalculate
  performance.
- Approval-mode balance updates apply to non-deposit task types when `amount > 0`.
- CBS validation can mark rejected/pending tasks as `cbsValidated`.
- No duplicate-task guard; one CBS row can match multiple tasks (`tasks.find` without
  consuming matches).
- Task amount/date validation is weak (negative/NaN/future dates, missing account/branch).

### Account mapping and product KPI mapping

- Product KPI mappings do not control KPI classification; scoring uses hardcoded
  `CBS_PRODUCT_TO_CATEGORY`. Adding a product in the UI does not make it count.
- `requiresCbs` and `min_balance` cannot be configured; min balance is hardcoded to 1000.
- Branch mapped-accounts endpoint crashed on unmapped accounts (`mappedTo.id` null);
  now null-safe.
- Staff account progress sums approved task amounts across all periods instead of
  using current balance − baseline and the same CBS/approval gate as scoring.
- The manual mapping UI is dead: View/Assign have no handlers, and the "Unmapped"
  filter maps to `status = Inactive`, not `mappedToId = null`.
- Auto-balance only processes `status = Inactive`, uses `Math.floor`, excludes
  supervisors, and is non-transactional.

### CBS validation

- **Critical:** Upload is non-transactional; failures leave partial balances, tasks,
  schedules, and a `Processing` validation record.
- Re-uploading the same file double-applies repayments; there is no idempotency key.
- CBS task matching ignores approval status and is not one-to-one.
- New CBS accounts are always created as `Savings`; missing balance defaults to 0 and
  can overwrite the existing balance. Loan/product classification is lost.
- Prior CBS validations are never superseded; old `cbsValidated` tasks keep scoring.
- Auto-mapping is too permissive (any approved task with matching account number) and
  the UI threshold (500) contradicts the backend (1,000).
- Discrepancy resolution is now scoped and audited, but the UI still has no discrepancy
  detail list/resolution flow.

### June baseline import

- Active-baseline deactivation now happens only after a successful parse/import, but the
  import is still non-transactional and row-by-row.
- Duplicate/negative/invalid rows are not rejected; duplicate account numbers can be
  ambiguous.
- Activating a period only deactivates other periods; it does not verify the period
  exists or that rows were imported.
- Missing baselines are now skipped (not treated as zero), so accounts created after the
  baseline do not inflate growth.

### Performance scoring and ratings

- **Critical:** No normal workflow generates `PerformanceScore` rows. The only path is
  `POST /api/performance/calculate`; no UI calls it and no scheduled job runs it.
- Staff plans use string periods (`FY-2026-27`) while behavioral evaluations use
  `Monthly/Quarterly/Annual`; `calculateKPIScore` requires the plan period, and behavioral
  lookup only runs for `Monthly/Quarterly/Annual`. Behavioral score is therefore always
  0 or calculation throws.
- Weights are now loaded once and normalized across present KPIs to an 85-point maximum,
  but the KPI framework still allows weights summing to ≠100; validation is still needed.
- Rating thresholds are now consistent (90/80/70/60) in backend and KPI framework UI,
  but dashboards still use different labels (`Very Good`, `Good`, `Needs Support`).
- Incremental growth still ignores the plan period, so historical scorecards show
  lifetime growth.
- Branch-manager scoring double-counts product plans under the same KPI category.
- Performance scores have no unique natural key and can overwrite locked/finalized rows.
- Read APIs ignore `year`/`month` query parameters used by the Monthly Scorecard.
- Team standings use hardcoded 40/30/30 weights and the wrong period.

### Behavioral evaluation

- **Critical:** `BehavioralInput` sends `employeeId`/`overallScore`/`submittedBy`, but the
  backend expects `evaluatedUserId`, `year`, `competencies`, etc. The request fails.
- Period values are `2024-Q1…Q4`, which are not valid `EvaluationPeriod` values.
- Evaluation list UI reads fields the backend does not return.
- Approval is not a real chain; there is no submit step, no branch/duplicate/lock rules.
- Competency Framework is UI-only; no create UI for most roles.

### NPL and collections

- Any authenticated user could mark any installment paid; now manager-only and
  branch-scoped, with amount/date validation.
- Schedule generation uses the wrong term, has no uniqueness constraint, and is
  non-transactional.
- Collection rate counts only installments due exactly today.
- Collection alerts exclude long-overdue accounts; `Missed` status and `daysPastDue`
  are never maintained.
- NPL snapshots are now unique per `(branch, date)`, but the GET still writes a snapshot;
  write-on-read should be removed.
- Zero schedules can close a loan; schedule reads are still not fully scoped.
- HQ area PAR90 amounts are reconstructed from rounded ratios.

### Teams, notifications, audit

- Team creation can leave orphan teams if member validation fails late; update is
  partially applied before validation; delete leaves members assigned.
- Notification deep links previously used `window.location.href` (fixed to same-origin
  router navigation). Some notification links still point to nonexistent routes.
- Production CORS did not allow `PATCH`, breaking mark-as-read; fixed.
- Notifications have missing types and no notifications to the next approver.
- Audit enum gaps meant plan creation, bulk mapping, baseline import/activation,
  product mapping, and transactions silently failed to audit; enums and mappings fixed.
- Audit filters still do not match stored enum values, and coverage is incomplete.
- Uploaded files are deleted but file paths remain in records.

### Schema / data integrity

- Money is stored as floating point; use `Decimal`/integer minor units for financial
  amounts and rounding.
- Missing uniqueness constraints on staff plans, task approvals, and performance scores.
- Inconsistent period/date models and timezone-sensitive day boundaries.
- Missing cascade/orphan handling for user deactivation, teams, and branches.
- Dead enums/fields and dead UI/API paths (mapping create/update, user reset/delete,
  exports, sub-team models).

### Seed scripts

- Several historical seeds reference removed models/roles/positions and fail
  (`seedAllUsers`, `seedFullHierarchy`, `seedTestData`, `seedFromFiles`).
- `seedWisdomSaccos` can leave broken references and inconsistent demo scores.
- Default/demo credentials are weak and widely shared; now only shown by the login UI
  in development builds.

## 7. Recommended next steps (in order)

1. Upgrade `xlsx`, `react-router-dom`, Vite/Vitest, `ws`, and transitive packages; rerun
   `npm audit`.
2. Make CBS upload, June import, bulk mapping, and plan cascade transactional; add
   idempotency keys and background job processing.
3. Replace the public user directory with an email-based login and add MFA for admins.
4. Enforce branch/area/self scope on exports, CBS, mappings, staff plans, and all
   financial reads.
5. Add route schema validation (Zod/express-validator) and remove remaining mass assignment.
6. Build a single period model and a scheduled performance-score calculation; align
   behavioral evaluation contracts and rating labels.
7. Refactor dashboard/NPL queries to grouped SQL/`groupBy`; stop writing snapshots on GET.
8. Add server-side pagination/search to all list pages and a shared frontend query cache.
9. Add integration tests for horizontal/vertical privilege escalation and workflow
   state transitions (task edit, CBS upload, baseline import, NPL payment).
